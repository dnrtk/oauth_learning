1. はじめに

「Google でログイン」「GitHub と連携する」——普段何気なく押しているこれらのボタンの裏側では、OAuth（オーオース） という仕組みが動いています。OAuth は仕様書を読むだけだと用語が多く抽象的に感じますが、実際に自分の手で作ってみると「なぜこの手順が必要なのか」が驚くほどすっきり理解できます。

この教材では、OAuth に登場する 3 つのサーバー（クライアント・認可サーバー・リソースサーバー）を すべて自分で、Python の標準ライブラリだけで実装します。Web フレームワークも OAuth ライブラリも使わないので、隠れた「魔法」はありません。ブラウザとサーバーの間を流れる HTTP のやりとりがすべてターミナルに表示されるので、目で見ながら理解を深められます。

この教材のゴール

  • OAuth が「何の問題を解決するのか」を自分の言葉で説明できる
  • 認可コードフローの各ステップで、誰が誰に何を送っているかを説明できる
  • state、PKCE、redirect_uri の完全一致検証などが「どんな攻撃を防いでいるのか」を説明できる
  • OAuth（認可）と OpenID Connect（認証）の違いを説明できる

進め方

  1. 2 章〜7 章を読んで、用語と全体の流れをつかみます（コードはまだ書きません）。
  2. 8 章で完成版を動かし、ブラウザとターミナルのログで実際の流れを観察します。
  3. 9 章の演習で、穴あきのコードを自分で埋めていきます。テストで答え合わせができます。
  4. 10 章で、わざと攻撃してみて対策の効果を確かめます。
  5. 11 章以降で、実務につながる発展的な話題を押さえます。

2. なぜ OAuth が必要なのか

2.1 パスワードを渡してしまう問題

次のような場面を考えてみましょう。あなたは「メモ管理サービス」にたくさんのメモを保存しています。そこへ、新しい「メモ閲覧アプリ」が登場しました。このアプリはメモ管理サービスのメモをきれいに一覧表示してくれるそうです。

OAuth が普及する前は、このような連携を実現するために メモ管理サービスの ID とパスワードをメモ閲覧アプリに入力する という方法がよく使われていました。アプリはそのパスワードで、あなたになりすましてメモ管理サービスにログインするわけです。

この方法には深刻な問題があります。

問題具体的に何が困るか
権限が大きすぎる「メモを読む」だけでよいのに、パスワードがあればメモの削除、パスワード変更、退会まで何でもできてしまう。
漏洩時の被害が大きいアプリがパスワードを保存していて、そのアプリが攻撃されるとパスワードそのものが漏れる。同じパスワードを他でも使い回していれば被害はさらに広がる。
取り消せないアプリとの連携だけをやめたくても、パスワードを変更するしかない。するとパスワードを渡した他のすべてのアプリも使えなくなる。
多要素認証と相性が悪いワンタイムパスワードなどを使っていると、アプリが代わりにログインすることがそもそもできない。

2.2 OAuth の解決策: 「合鍵」ではなく「期限付きの専用キー」を渡す

ホテルを思い浮かべてください。ホテルはお客さんに建物のマスターキーを渡しません。フロントで本人確認をしたうえで、その部屋だけを、宿泊期間中だけ開けられる カードキー を発行します。カードキーを無くしても、フロントで無効化すれば済みます。

OAuth はこれと同じ発想です。

  • あなたは、パスワードを メモ管理サービス自身（の認可サーバー）にだけ 入力します。
  • メモ管理サービスは、あなたの同意を得たうえで、メモ閲覧アプリに アクセストークン という「カードキー」を発行します。
  • アクセストークンには「メモの読み取りだけ」といった 権限の範囲（スコープ） と 有効期限 があり、いつでも 取り消し できます。
✔ ポイント

OAuth の本質は「パスワードを渡さずに、限定された権限だけを第三者アプリに委ねる」ことです。これを 権限の委譲（delegation） と呼びます。

3. 認証と認可の違い

認証系の話で最初につまずきやすいのが、よく似た 2 つの言葉です。

認証（Authentication, AuthN）認可（Authorization, AuthZ）
問いあなたは 誰 ですか？あなたは 何をしてよい ですか？
身近な例空港で パスポートを見せて本人確認する搭乗券に書かれた便・座席にだけ乗れる
Web での例ID とパスワードでログインする「このアプリはメモの読み取りだけ可能」
代表的な仕組みパスワード、多要素認証、OpenID ConnectOAuth 2.0

OAuth は「認可」のための仕組みです。名前の Auth は Authorization の略です。OAuth の流れの中でユーザーはログイン（認証）をしますが、それは認可サーバーが「誰が許可を出しているのか」を確かめるための手段にすぎず、OAuth の目的そのものではありません。

⚠ よくある誤解

「OAuth でログイン」という表現をよく目にしますが、素の OAuth 2.0 をそのまま「ログイン（認証）」に使うと安全でない場合があります。認証に使いたいときは OAuth を拡張した OpenID Connect を使います。理由は11 章で説明します。

5. 前提となる Web の仕組み

OAuth は新しい通信技術を発明したわけではなく、既存の HTTP の機能を組み合わせた「手順の取り決め」です。そのため、以下の Web の基本を押さえておくと理解がぐっと楽になります。知っている項目は読み飛ばして構いません。

5.1 HTTP リクエストとレスポンス

ブラウザやプログラムはサーバーに リクエスト を送り、サーバーは レスポンス を返します。リクエストには「メソッド（GET / POST など）」「パス」「ヘッダー」「ボディ」があり、レスポンスには「ステータスコード（200, 302, 401 など）」「ヘッダー」「ボディ」があります。

GET /api/profile HTTP/1.1          ← メソッドとパス
Host: 127.0.0.1:9100              ← ヘッダー
Authorization: Bearer abc123...   ← ヘッダー (後で出てくるアクセストークン)

HTTP/1.1 200 OK                   ← ステータスコード
Content-Type: application/json

{"name": "Alice Liddell", ...}    ← ボディ

5.2 クエリパラメータと URL エンコード

URL の ? 以降は クエリパラメータ と呼ばれ、key=value を & でつないで値を渡します。値に / や :、空白などの特別な文字が含まれる場合は URL エンコード（%2F のような形への変換）が必要です。Python では urllib.parse.urlencode() が自動でやってくれます。

>>> urllib.parse.urlencode({"redirect_uri": "http://127.0.0.1:8000/callback", "scope": "profile notes:read"})
'redirect_uri=http%3A%2F%2F127.0.0.1%3A8000%2Fcallback&scope=profile+notes%3Aread'

5.3 リダイレクト（302）— OAuth の主役

サーバーがステータス 302 Found と Location ヘッダーを返すと、ブラウザは 自動的に その URL へ移動します。

HTTP/1.1 302 Found
Location: http://127.0.0.1:9000/authorize?response_type=code&client_id=demo-client&...

OAuth では、クライアントと認可サーバーが ブラウザをリダイレクトで行き来させることで、ユーザーを介してメッセージを受け渡します。「クライアント → 認可サーバー」へのメッセージは URL のクエリに載せてブラウザに運ばせ、「認可サーバー → クライアント」への返事も同じようにリダイレクトで運ばせます。

5.4 Cookie とセッション

HTTP は本来、前のリクエストのことを覚えていません。そこでサーバーは Set-Cookie ヘッダーでブラウザにランダムな セッション ID を預け、ブラウザは以降のリクエストでそれを Cookie ヘッダーで送り返します。サーバーはセッション ID をキーにして「このブラウザは alice としてログイン済み」などの情報をサーバー側に保存しておきます。これが セッション です。

ℹ この教材での注意点

クライアントと認可サーバーは それぞれ別のセッション を持っています（Cookie 名は client_session と as_session）。「認可サーバーにログインしている」ことと「クライアントがトークンを持っている」ことは別の状態です。この区別は OAuth を理解するうえでとても大切です。

5.5 フロントチャネルとバックチャネル

OAuth の通信は、通り道によって 2 種類に分けて考えます。この区別が OAuth のセキュリティ設計を理解する鍵です。

フロントチャネルバックチャネル
通り道ブラウザを経由する（リダイレクトの URL に載せる）サーバー同士が直接 HTTP 通信する
例認可リクエスト、認可コードの返却トークンリクエスト、イントロスペクション
安全性低い。URL はブラウザの履歴、アクセスログ、拡張機能、Referer ヘッダーなどから 漏れる可能性がある。ユーザーや攻撃者が 改ざんすることもできる。高い。TLS で保護された 1 対 1 の通信で、相手を認証できる。
載せてよいもの漏れても単体では悪用しにくいもの（短命・使い捨ての認可コードなど）秘密情報（client_secret、アクセストークン）

教材のログでは、バックチャネル通信に ※バックチャネル (ブラウザを経由しない直接通信) と表示されます。

5.6 Base64 と Basic 認証

Base64 はバイト列を英数字と記号だけの文字列に変換する方式です（暗号化ではなく、誰でも元に戻せます）。Basic 認証 は ID:パスワード を Base64 にして Authorization: Basic ... ヘッダーで送る、HTTP 標準の認証方式です。OAuth ではクライアントが自分の client_id と client_secret を送るのによく使われます。

Authorization: Basic ZGVtby1jbGllbnQ6ZGVtby1jbGllbnQtc2VjcmV0
                     └─ "demo-client:demo-client-secret" を Base64 にしたもの

6. 認可コードフローの全体像

OAuth 2.0 にはいくつかの「フロー（grant type）」がありますが、Web アプリでもスマホアプリでも推奨されるのは 認可コードフロー（Authorization Code Grant） です。この教材ではこれを実装します。

大きく 4 つのフェーズに分けると理解しやすくなります。

フェーズ A: 認可リクエスト（①〜③）

クライアントはユーザーを認可サーバーへリダイレクトします。このとき「どのアプリが（client_id）」「どんな権限を（scope）」「結果をどこに返してほしいか（redirect_uri）」をクエリに載せます。

GET /authorize?response_type=code
    &client_id=demo-client
    &redirect_uri=http%3A%2F%2F127.0.0.1%3A8000%2Fcallback
    &scope=profile+notes%3Aread
    &state=Xk3pQ...（ランダム値） HTTP/1.1
Host: 127.0.0.1:9000
パラメータ意味
response_type=code「認可コードフローで、認可コードを返してください」という宣言
client_id事前に認可サーバーへ登録したクライアントの ID（公開情報）
redirect_uri認可コードの返送先。事前登録した値と 完全一致 しなければならない
scope求める権限。スペース区切り
stateクライアントが生成したランダム値。CSRF 攻撃を防ぐ（10 章）

フェーズ B: ユーザーの認証と同意（④〜⑦）

認可サーバーはユーザーにログインしてもらい（すでにログイン済みならスキップ）、「メモ閲覧アプリが、プロフィールとメモの読み取りを求めています。許可しますか？」という 同意画面 を表示します。パスワードを入力する相手は認可サーバーであり、クライアントではありません。

フェーズ C: 認可コードの受け取りと交換（⑧〜⑫）

ユーザーが許可すると、認可サーバーは 認可コード（短命で使い捨ての引換券）を発行し、ブラウザを redirect_uri へリダイレクトします。

HTTP/1.1 302 Found
Location: http://127.0.0.1:8000/callback?code=SplxlOBeZQ...&state=Xk3pQ...

クライアントは state を検証した後、バックチャネル で認可コードをトークンと交換します。このとき client_secret で自分が本物のクライアントであることを証明します。

POST /token HTTP/1.1
Host: 127.0.0.1:9000
Authorization: Basic ZGVtby1jbGllbnQ6ZGVtby1jbGllbnQtc2VjcmV0
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQ...&redirect_uri=http%3A%2F%2F127.0.0.1%3A8000%2Fcallback
{
  "access_token": "2YotnFZFEjr1zCsicMWpAA...",
  "token_type": "Bearer",
  "expires_in": 120,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA...",
  "scope": "profile notes:read"
}
ℹ なぜ直接トークンを返さず、わざわざ「コード」を挟むのか？

認可サーバーからクライアントへの返事はブラウザ経由（フロントチャネル）なので、URL が履歴やログに残るなど漏れやすい経路です。そこにアクセストークンを直接載せると、漏れたら即座に悪用されます。

そこで、フロントチャネルには 単体では使えない引換券（認可コード） だけを載せ、本物のトークンは安全なバックチャネルで、クライアント認証付きで 受け取るようにしています。認可コードは「短命（この教材では 60 秒）」「1 回限り」なので、漏れても被害を抑えられます。さらに PKCE（演習 7）を使えば、漏れたコードを第三者が交換することもできなくなります。

フェーズ D: API の呼び出し（⑬〜⑱）

クライアントは Authorization: Bearer <アクセストークン> ヘッダーを付けて API を呼び出します。リソースサーバーはトークンが有効か、必要なスコープを持っているかを確かめ、そのトークンの持ち主（alice）のデータだけを返します。

この教材では、リソースサーバーは認可サーバーの イントロスペクションエンドポイント（RFC 7662）に「このトークンは有効？」と問い合わせて確認します。もう一つの代表的な方式（JWT）は次章で紹介します。

7. トークンとスコープ

7.1 アクセストークンは「持参人払い」

アクセストークンの token_type は Bearer（持参人）です。これは「このトークンを持ってきた人は誰であれ、権限を持つものとして扱う」という意味です。お金の引換券と同じで、盗まれたら盗んだ人が使えてしまいます。だからこそ、

  • 有効期限を短くする（この教材では 120 秒。実務では数分〜1 時間程度）
  • 必ず HTTPS で送る
  • URL のクエリに載せず、Authorization ヘッダーで送る
  • ログや画面に出さない（この教材は学習のためにあえて表示しています）

といった対策が取られます。

7.2 スコープ — 権限の範囲

スコープ は「このトークンで何ができるか」を表す文字列です。この教材では次の 2 つを用意しています。

スコープ意味必要な API
profileプロフィール（名前・メールアドレス）の読み取りGET /api/profile
notes:readメモの読み取りGET /api/notes

スコープの名前や粒度はサービスごとに自由に決められます（例: GitHub の repo、Google の https://www.googleapis.com/auth/drive.readonly）。クライアントは 必要最小限 のスコープだけを要求するのがマナーです。

7.3 リフレッシュトークン

アクセストークンを短命にすると、頻繁に期限切れになります。そのたびにユーザーに同意画面を見せるのは不便です。そこで、トークンエンドポイントは長命の リフレッシュトークン も一緒に返します。クライアントはアクセストークンが切れたら、リフレッシュトークンを使って（バックチャネルで）新しいアクセストークンをもらいます。

リフレッシュトークンは 認可サーバーにだけ送り、リソースサーバーには決して送りません。この教材では、使うたびに新しいリフレッシュトークンに入れ替える ローテーション も実装します（演習 8）。

7.4 トークンの中身: 不透明トークンと JWT

不透明（opaque）トークンJWT（JSON Web Token）
中身意味のないランダム文字列。情報は認可サーバーの DB にあるユーザー・スコープ・期限などを JSON にして電子署名したもの
検証方法認可サーバーに問い合わせる（イントロスペクション）リソースサーバーが署名と期限を自分で検証する
長所即座に失効できる。中身が漏れない問い合わせが不要で速い
短所API 呼び出しのたびに問い合わせが発生する期限前の失効が難しい。署名検証の実装を誤ると危険

この教材は仕組みが見えやすい 不透明トークン + イントロスペクション を採用しています。

ブラウザとターミナルを左右に並べて、次の手順で進めてください。各ページの 上部の色帯 で、いまどのサーバーの画面にいるかが分かります（青 = クライアント、橙 = 認可サーバー、紫 = リソースサーバー）。

  1. http://127.0.0.1:8000 を開き、「認可サーバーと連携する」を押します。
    ターミナルに [クライアント] → 302 Location: http://127.0.0.1:9000/authorize?... と表示され、ブラウザが認可サーバーへ移動したことが分かります。アドレスバーの URL にも client_id や state が見えるはずです。
  2. 認可サーバーのログイン画面で alice / alice-pass を入力します。
    ログでは password = ******** と隠していますが、パスワードが届いているのは 認可サーバーだけ であることを確認してください。
  3. 同意画面で「許可する」を押します。
    [認可サーバー] → 302 Location: http://127.0.0.1:8000/callback?code=...&state=... の直後に、[クライアント] → POST http://127.0.0.1:9000/token ※バックチャネル が続くのを確認しましょう。
  4. クライアントのトップページに戻り、受け取ったトークンが表示されます。「プロフィールを取得」を押します。

  6. 2 分待ってから再度「プロフィールを取得」を押すと 401 になります。「トークンを更新 (refresh)」を押すと再び取得できるようになります。
  7. ダッシュボードで「許可を取り消す」を押してから API を呼ぶと、やはり 401 になります。これがパスワード方式ではできなかった「連携だけの取り消し」です。

演習 2: 認可リクエストを検証する ［認可サーバー］

やること

auth_server.py の validate_authorization_request() を実装します。フロー図の③で、認可サーバーが最初に行う処理です。

考え方: 2 種類のエラー

認可リクエストのエラーには、クライアントにエラーを返してよいもの と 返してはいけないもの があります。

エラーの種類例対応この教材での例外
リダイレクト先が信用できない未登録の client_id、登録と違う redirect_uriリダイレクトせず、認可サーバーの画面でエラー表示UntrustedRedirectError
それ以外response_type が違う、未知の scoperedirect_uri へ error=... 付きでリダイレクトOAuthError

なぜ前者はリダイレクトしてはいけないのでしょうか。もし認可サーバーが「redirect_uri が不正です」というエラーを、その不正な redirect_uri にリダイレクトして伝えたとします。すると攻撃者は https://accounts.example.com/authorize?redirect_uri=https://evil.example/ のような 信頼できるドメインの URL を作るだけで、ユーザーを自分のサイトへ誘導できてしまいます。これを オープンリダイレクタ と呼びます。

考え方: redirect_uri は完全一致で

redirect_uri の検証は「前方一致」や「ドメインが同じなら OK」ではなく、登録値との完全一致（文字列比較） で行います。部分一致を許すと、http://127.0.0.1:8000/callback/../evil や ...?next=https://evil.example/ のような細工で、認可コードを攻撃者が用意したページへ流出させられる恐れがあるためです。現在のセキュリティのベストプラクティス（RFC 9700）でも完全一致が求められています。

確認

演習 3: 認可コードを発行する ［認可サーバー］

やること

  • 3-1 AuthorizationServer.issue_authorization_code(): 認可コードを生成し、誰がどのクライアントに何を許可したかと一緒に保存する
  • 3-2 build_authorization_response_url(): 認可コードと state を載せたリダイレクト先 URL を作る

ユーザーが同意画面で「許可する」を押した直後（フロー図の⑧）の処理です。

考え方

認可コードは引換券なので、次の性質が必要です。

  • 推測できない: 連番や時刻ベースではなく、暗号論的に安全な乱数（secrets モジュール）で作る。Python の random モジュールは予測可能なので使ってはいけません。
  • 短命: 発行から数十秒〜数分で失効させる（RFC 6749 は最大 10 分を推奨）。
  • 紐づけ: 後でトークンと交換するときに「誰の許可か」「どのクライアント宛てか」「どの redirect_uri で要求されたか」を照合できるよう、一緒に保存する。

state は認可リクエストで受け取った値を そのまま 返します。認可サーバーは state の中身を解釈しません。

考え方: state の役割

考え方: リソースサーバーの判定順序

用意済みの ResourceServer._protected() は、次の順で判定します（RFC 6750）。

状況レスポンス
トークンが付いていない401 + WWW-Authenticate: Bearer realm="..."
トークンが無効・期限切れ・取り消し済み401 + WWW-Authenticate: Bearer error="invalid_token"
トークンは有効だがスコープが足りない403 + WWW-Authenticate: Bearer error="insufficient_scope"

401 Unauthorized は「誰だか分からない（認証情報が無い・無効）」、403 Forbidden は「誰だかは分かったが権限が無い」という使い分けです。

演習 7: PKCE ［クライアント・認可サーバー］

PKCE とは

PKCE（Proof Key for Code Exchange、「ピクシー」と読みます。RFC 7636）は、認可コードを盗まれても、盗んだ人がトークンと交換できないようにする 仕組みです。もともとは秘密を持てないスマホアプリ（パブリッククライアント）のために作られましたが、現在はコンフィデンシャルクライアントも含めて すべてのクライアントで使うことが推奨 されています（RFC 9700、OAuth 2.1）。

ポイントは ハッシュ関数（SHA-256）の一方向性 です。ハッシュ値から元の値を逆算することは事実上できません。フロントチャネルを盗み見た攻撃者は code_challenge（ハッシュ値）と code は手に入れられても、code_verifier（合言葉）は分からないので、トークンリクエストに成功しません。

また、code_verifier はフローごとに新しく作ってクライアントのセッションに保存するので、「このトークンリクエストは、あの認可リクエストを出したのと同じクライアントのセッションから来た」ことの証明にもなります。これにより、盗んだ認可コードを 別のセッションに注入する攻撃（認可コードインジェクション）も防げます。

やること

  • 7-1 pkce.generate_code_verifier(): 43〜128 文字のランダムな合言葉を作る
  • 7-2 pkce.compute_code_challenge(): BASE64URL(SHA256(code_verifier))（パディングの = なし）を計算する
  • 7-3 pkce.verify_pkce(): 認可サーバー側で、code_verifier と保存しておいた code_challenge を照合する
  • 7-4 auth_server.extract_pkce_challenge(): 認可リクエストから code_challenge を取り出して検証する（S256 のみ受け付ける）

クライアント側で code_verifier を作ってセッションに保存し、code_challenge を認可リクエストに付ける処理は、用意済みの ClientApp._login() がすでに行っています。演習 1 と 4 で code_challenge / code_verifier 引数を扱っておいたのはこのためです。

ℹ Base64URL とは

通常の Base64 は + / = を使いますが、これらは URL の中で特別な意味を持ちます。Base64URL は + を -、/ を _ に置き換え、末尾の = を取り除いた、URL に安全な変種です。Python では base64.urlsafe_b64encode() の結果から = を rstrip します。

考え方: リフレッシュトークンローテーション

リフレッシュトークンは長命なので、盗まれたときの被害が大きくなります。そこで 使うたびに新しいリフレッシュトークンを発行し、古いものは無効にする のがローテーションです。

さらに、すでに使われた（無効化された）古いリフレッシュトークンが再び送られてきたら、それは「正規のクライアントと攻撃者のどちらかが、盗まれたトークンを使っている」ことを意味します。認可サーバーにはどちらが正規か分からないので、その許可（grant）から発行したトークンをすべて失効させます。正規のユーザーはもう一度同意し直す必要がありますが、攻撃者も締め出せます。

この教材では、最初の認可コードの値を grant_id として各トークンに記録し、revoke_grant(grant_id) で一括失効できるようにしています。

10. 攻撃と対策を体験する

セキュリティ対策は「なぜ必要か」が実感しにくいものです。ここでは完成した実装（自分のものでも solution でも構いません）を使って、実際に攻撃を試してみます。

10.1 state が無いと何が起きるか（CSRF / ログイン CSRF）

CSRF（Cross-Site Request Forgery） は、被害者のブラウザに、本人の意図しないリクエストを送らせる攻撃です。OAuth のコールバックに対する CSRF は次のように進みます。

state があれば、被害者のブラウザのセッションには攻撃者のフローの state が保存されていないので、⑤の時点で「state が一致しません」と拒否できます。

試してみよう

  1. クライアントで「連携する」→ ログイン → 同意 と進め、トークン取得後のトップページを表示します。
  2. ターミナルのログから [クライアント] ← GET /callback の直前にある Location: http://127.0.0.1:8000/callback?code=...&state=... をコピーします。
  3. state= の値を書き換えた URL をブラウザで開きます。→「state が一致しません」と表示されるはずです。
  4. 書き換えずにそのまま開いても拒否されます。state は使い捨てで、1 回目のコールバックで消去済みだからです。

10.2 認可コードの再利用

  1. 10.1 と同じようにコールバック URL の code を控えます。
  2. 次のコマンドで、同じコードをもう一度トークンと交換してみます（<CODE> を置き換え。PowerShell では curl.exe と書き、行末の \ を取り除いて 1 行で実行します）。 
    curl -i -X POST http://127.0.0.1:9000/token \
  -u demo-client:demo-client-secret \
  -d grant_type=authorization_code -d code=<CODE> \
  -d redirect_uri=http://127.0.0.1:8000/callback
    → {"error": "invalid_grant", "error_description": "この認可コードは使用済みです"} が返ります。
  3. クライアントで「プロフィールを取得」を押すと 401 になります。コードの再利用を検知した認可サーバーが、そのコードから発行したトークンを失効させたためです。認可サーバーのダッシュボードでも「失効」になっているのを確認しましょう。

10.3 redirect_uri の改ざん

認可サーバーに次の URL で直接アクセスしてみてください（redirect_uri が攻撃者のサイトになっています）。

http://127.0.0.1:9000/authorize?response_type=code&client_id=demo-client&redirect_uri=https%3A%2F%2Fevil.example%2Fcallback&scope=profile&state=x

→ リダイレクトされず、認可サーバーの画面で「redirect_uri が登録されている値と一致しません」と表示されます。もし認可サーバーがここで evil.example に認可コードを送ってしまったら、攻撃者はユーザーのデータにアクセスできてしまいます。

比較として、上の URL の redirect_uri を正しい値（http%3A%2F%2F127.0.0.1%3A8000%2Fcallback）に戻し、代わりに scope=admin と不正なスコープにしてみてください。今度はクライアントのコールバックへリダイレクトされ、アドレスバーの URL に error=invalid_scope が付いていることが確認できます。redirect_uri が正しいと確認できたので、エラーをクライアントに返してよいわけです（クライアントの画面には「state が一致しません」と表示されますが、これはクライアントを経由せずに直接 URL を開いたためで、正しい挙動です）。

10.4 PKCE が無いと何が起きるか（認可コードの横取り）

認可コードはフロントチャネルを通るため、次のような経路で漏れる可能性があります。

  • スマホで、悪意のあるアプリが正規アプリと同じカスタム URL スキーム（myapp://callback）を登録してコールバックを横取りする
  • ブラウザ履歴、プロキシやサーバーのアクセスログ、Referer ヘッダー、悪意あるブラウザ拡張

パブリッククライアントには client_secret が無いので、コードさえ手に入れば誰でもトークンと交換できてしまいます。PKCE があれば、交換には code_verifier が必要なので失敗します。

試してみよう

攻撃者が認可コードだけを盗み見た状況を再現します。

  1. PKCE 有効（--no-pkce なし）で起動し、ブラウザで次の URL を直接開きます。RFC 7636 の例の code_challenge を付けた認可リクエストです。 
    http://127.0.0.1:9000/authorize?response_type=code&client_id=demo-client&redirect_uri=http%3A%2F%2F127.0.0.1%3A8000%2Fcallback&scope=profile&state=demo&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256
  2. ログインして「許可する」を押すと、クライアントのコールバックに戻りますが、クライアントは「state が一致しません」と拒否します（クライアント自身が始めたフローではないため）。このおかげで 認可コードは未使用のまま 残ります。アドレスバーの URL から code の値を控えてください。
  3. 攻撃者になったつもりで、code_verifier を知らないままトークンと交換してみます（<CODE> を置き換え）。 
    curl -i -X POST http://127.0.0.1:9000/token   -u demo-client:demo-client-secret   -d grant_type=authorization_code -d code=<CODE>   -d redirect_uri=http://127.0.0.1:8000/callback
    → {"error": "invalid_grant", "error_description": "code_verifier が正しくありません (PKCE)"} で拒否されます。
  4. 今度は正しい合言葉を付けてみます。末尾に -d code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk を足して実行すると、トークンが発行されます。合言葉を知っている者だけが交換できる ことが確認できました。

PowerShell では curl の代わりに curl.exe と書き、行末の \ を取り除いて 1 行で実行してください。

11. OAuth と OpenID Connect

この教材のクライアントは、/api/profile を呼んで「alice さんのデータだ」と表示しています。これを見ると「OAuth でログイン機能が作れる」と思うかもしれません。しかし、アクセストークンは「このトークンを持つ人に、このデータへのアクセスを許可する」という証明であって、「いまアクセスしているのが alice 本人だ」という証明ではありません。

11.1 素の OAuth を認証に使う危険

例えば、悪意のあるアプリ X が、自分のユーザーから集めたアクセストークンを持っていたとします。もし別のアプリ Y が「受け取ったアクセストークンで /api/profile を呼べて、alice と返ってきたら、alice としてログインさせる」という作りだったら、X の運営者は alice のトークンを Y に渡すだけで、Y に alice としてログインできてしまいます。アクセストークンには「どのアプリ宛てに発行されたか」が含まれているとは限らないためです（トークン置き換え攻撃）。

11.2 OpenID Connect（OIDC）

OpenID Connect は、OAuth 2.0 の上に「認証」のための仕組みを足した仕様です。認可コードフローの scope に openid を含めると、トークンレスポンスに ID トークン が追加されます。

アクセストークン（OAuth）ID トークン（OIDC）
目的API にアクセスするための鍵（認可）ユーザーが誰で、いつどう認証されたかの証明書（認証）
宛先リソースサーバークライアント自身
形式決まっていない（不透明 / JWT）必ず署名付き JWT
主な中身スコープ、期限などiss（発行者）、sub（ユーザー ID）、aud（宛先クライアント）、exp、nonce など

ID トークンには aud（このトークンはどのクライアント宛てか）が必ず含まれ、クライアントは署名と aud を検証します。これにより 11.1 の攻撃を防げます。「Google でログイン」などの実際のソーシャルログインは、ほぼすべて OpenID Connect です。

クライアント実装のチェックリスト

  • 認可コードフロー + PKCE（S256）を使っている
  • state（または OIDC の nonce）を毎回生成し、検証している
  • 要求するスコープは最小限
  • アクセストークン・リフレッシュトークンはサーバー側に保存し、ブラウザの localStorage などには置かない（SPA の場合は BFF パターンも検討）
  • ログインが目的なら OAuth ではなく OpenID Connect の ID トークンを検証している

14. 用語集

用語意味
アクセストークンAPI にアクセスするための、期限とスコープ付きの鍵。持っている人が使える（Bearer）。
イントロスペクションリソースサーバーが認可サーバーに「このトークンは有効か」を問い合わせる仕組み（RFC 7662）。
オープンリダイレクタ任意の URL へリダイレクトさせられてしまう脆弱性。フィッシングなどの踏み台になる。
クライアントユーザーのデータを使いたい第三者アプリ。ブラウザのことではない。
クライアント認証クライアントが client_secret などで自分が本物であることを認可サーバーに証明すること。
グラント（grant）ユーザーがクライアントに与えた「許可」。またはトークンを得る方式（grant type）。
コールバック / リダイレクト URI認可サーバーが認可コードを返すクライアント側の URL。事前登録が必要。
コンフィデンシャル / パブリッククライアント秘密（client_secret）を安全に保管できるか否かによる分類。
スコープトークンで何ができるかを表す文字列。
セッションCookie に入れた ID をキーに、サーバー側で利用者の状態を覚えておく仕組み。
同意画面「このアプリに次の権限を与えますか？」とユーザーに確認する認可サーバーの画面。
認可コード同意の結果としてフロントチャネルで渡される、短命・使い捨ての引換券。
認可サーバーユーザーを認証し、同意を得て、トークンを発行するサーバー。
バックチャネルサーバー同士の直接通信。秘密情報を扱える。
フロントチャネルブラウザのリダイレクトを経由する通信。漏洩・改ざんの可能性がある。
リソースオーナーデータの持ち主（ユーザー）。
リソースサーバーデータを持つ API サーバー。トークンを検証してからデータを返す。
リフレッシュトークンアクセストークンを再発行してもらうための長命なトークン。認可サーバーにだけ送る。
CSRF被害者のブラウザに意図しないリクエストを送らせる攻撃。OAuth では state で防ぐ。
ID トークンOpenID Connect で発行される、ユーザーの認証結果を表す署名付き JWT。
JWTJSON に電子署名を付けたトークン形式。中身を受け取った側で検証できる。
PKCEcode_verifier / code_challenge により、認可コードの横取りを無力化する拡張（RFC 7636）。
stateクライアントが認可リクエストに付けるランダム値。コールバック時に照合して CSRF を防ぐ。
